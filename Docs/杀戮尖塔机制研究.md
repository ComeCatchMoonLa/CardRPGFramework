# 杀戮尖塔机制研究（Phase 2+ 设计输入）

> **一句话结论：杀戮尖塔的底层不是"卡牌游戏"，而是"行动队列驱动的战斗模拟器"——一切改变战斗状态的事情都是排队执行的 Action；一切持续状态都是挂在生物身上的 Power，通过钩子在固定时机触发行为或修改数值。原版没有独立的 RuleSystem，本项目把"数值修改钩子"独立成 RuleSystem 属于自己的差异化设计。**

本文是对《杀戮尖塔》一代（公开 wiki、补丁说明与 Mod 社区对反编译源码的还原）与二代（Godot 4 + C# 是官方公开信息；分层来自第三方整理，见第 1 节）实现机制的调研归纳，作为 Phase 2 及以后设计 ActionSystem / EffectSystem / BuffSystem / RuleSystem 时的事实依据。Phase 1 范围不受本文影响，见 [`开发计划/Ver 0.x/0.1/Phase 1/游戏设计.md`](开发计划/Ver%200.x/0.1/Phase%201/游戏设计.md)。0.1 之后各版本怎么用本文，见 [`开发计划/README.md`](开发计划/README.md)。

> **核对状态（2026-09）**：已按 wiki.gg 专题页（含 Order / Interactions 小节）与官方补丁说明逐条核对。本次更正：第 2 节回合时序（能量重置早于回合开始效果；怪物先清格挡再毒发；bakabird 分层降为观测模型）、第 3 节格挡公式只对卡牌格挡成立、第 4 节头槌与满手抽牌、第 7 节冰淇淋语义、第 1 节二代资料降级。各来源可信度与写规则时的优先级见文末。

## 1. 官方实现架构

### 一代（Java + libGDX，Mod 社区还原）

四个支柱：

```text
AbstractGameAction  一次性行为（伤害、抽牌、施加能力…），进入 GameActionManager 队列按序执行
AbstractPower       持续状态（力量、中毒、易伤…），挂在生物的能力列表上，通过重写钩子生效
AbstractRelic       遗物，无独立机制，复用同一套钩子 + Action
AbstractCreature    生物（玩家/怪物公共基类），持有生命、格挡、Power 列表
```

关键机制：

- 卡牌的 `use()` 不直接改数据，而是 `addToBot(new DamageAction(...))` 把行为加入队列。
- Power 的钩子分两类，**这是理解 Effect/Buff/Rule 关系的钥匙**：
  1. **触发型钩子**：时机到了就做事，通常再入队新 Action。例：中毒在所有者回合开始入队一个扣血行为。
  2. **数值修改型钩子**：计算数值时被调用，返回修改后的值，不做任何事。例：力量的 `atDamageGive` 返回 `damage + 层数`。
- 施加、减层、移除 Power 本身也是 Action（`ApplyPowerAction` / `ReducePowerAction` / `RemovePowerAction`），因此人工制品才能"拦截下一个负面能力"——它拦的是队列里的施加行为。

### 二代（Godot 4 + C#；分层为第三方整理，未经官方确认）

下面这份分层来自 [Hexpion/Slay-the-spire-2](https://github.com/Hexpion/Slay-the-spire-2) 仓库，属于对泄漏 / 反编译内容的第三方整理；截至 2026-09 该仓库的 `ARCHITECTURE.md` 是**空文件**，不是 MegaCrit 发布的架构承诺。能当事实用的只有「二代用 Godot 4 + C#」这一点（官方公开）。列在这里只作旁证：


局内/局外状态分离、配置定义到运行实体的显式转换（`CardData → CardDefinition`）是本项目自己的判断，二代资料只算旁证，**不能**拿它证明本项目要做 Replay 或事件总线。

## 2. 回合时序（一代）

先给**原版引擎真实的钩子结构**，再给 bakabird 的观测分层——后者是解释现象的模型，不是官方回调名。

### 2.1 引擎结构：三档 Power 钩子 + 怪物按阵营批处理

一代 `AbstractPower` 与回合相关的钩子只有 `atStartOfTurn`（另有抽牌后的 `atStartOfTurnPostDraw`）/ `atEndOfTurn(isPlayer)` / `atEndOfRound` 三档；多怪物时的差别只在于**先对全部怪物跑完回合开始，再逐只 `takeTurn`**。

| 阶段 | 发生的事（按顺序） |
| --- | --- |
| 战斗开始 | 构建牌堆并洗牌 → 抽起手 5 张 → 遗物开战钩子（按拾取顺序）→ 怪物展示首个意图。痛楚印记的 2 张伤口在起手抽完后才洗进抽牌堆，所以默认第一手抽不到 |
| 玩家回合开始 | 清格挡（路障 / 模糊例外）→ **能量重置为上限**（冰淇淋：当前能量 += 上限）→ 抽 5 张 → 回合开始效果。狂暴的 +1 能量、恶魔形态、残杀都在能量重置**之后**结算，不会被抹掉；源码把回合开始钩子分抽牌前 / 抽牌后两档，做具体能力时按该能力核对 |
| 玩家回合中 | 打牌，每张牌展开为一串 Action 入队执行；喝药不计打出 |
| 玩家回合结束 | 遗物 → Power（金属化、镀层护甲）→ 手牌中的结束时结算牌（燃烧、悔恨）→ 弃手（保留牌例外）。「遗物 → Power → 牌」见 wiki.gg Mechanics 与 V2.0 补丁说明 |
| 怪物回合开始 | **每只怪物先清格挡（路障 / 模糊例外），再结算它的回合开始 Power（中毒）**；全部怪物走完这一步，才有任何一只出手。所以「全体毒发早于任何出手」；又因为清格挡在毒发之前，守护者被毒发切进防御形态拿到的格挡会留到玩家回合（wiki.gg Poison） |
| 怪物依次出手 | 从左到右执行意图；每只在自己出手末尾决定并展示下轮意图 |
| 怪物回合结束 → 轮结束 | 怪物的回合结束 Power（仪式、金属化）在它出手之后、玩家回合之前结算；随后所有生物跑 `atEndOfRound`：虚弱 / 易伤 / 脆弱减 1 层，带 `justApplied` 的跳过一次 |

### 2.2 bakabird 的观测分层（解释模型，不是 API）

[bakabird 的实测记录](https://www.cnblogs.com/bakabird/p/slaythesprite.html)用六个时点解释上面的现象：

```text
回合行动开始 > 阵营行动开始 > 角色行动开始 > 角色行动结束 > 阵营行动结束 > 回合行动结束
```

它对「毒是全体一起发、金属化是各自结束时发、减层在轮末」的解释成立，但原文是一篇 569 次阅读的个人观测笔记，不是反编译。本文旧版把它写成「原文精度的四级结算结构」并要求触发器区分四级挂载点，过满：一代实际只有上面三档钩子，加上「怪物先全体回合开始、再逐只出手」这一条批处理规则。

要点：

- **格挡在「自己回合开始」清零**，不是回合结束——所以防御牌能挡住紧随其后的敌人攻击。Phase 1 游戏设计与此一致。
- **多怪物真正需要的能力**：怪物侧的「回合开始」是对全体怪物的批处理（先清格挡、再中毒），全部做完才逐只出手；「回合结束」在出手之后、玩家回合之前；再加一个轮末减层时点。不必做成六个官方回调名，也不必为玩家和怪物各设两级。
- **回合型 debuff 在轮结束统一减层**，不在各自行动内减；`justApplied` 由构造参数 `isSourceMonster`（施加者是不是怪物）决定，不是「所有者是否已行动完」的通用判断（见 [`开发计划/Ver 0.x/0.7/游戏设计.md`](开发计划/Ver%200.x/0.7/游戏设计.md) 第 4 节）。
- **怪物在自己出手末尾就决定下回合意图**，玩家回合全程可见，这是意图系统的本质：先斩后奏的反面。
- 能量默认不累积：回合开始「当前能量 = 上限」。冰淇淋不是跳过这一步，而是把它换成「当前能量 += 上限」（上限 3、剩 2 → 5）。

## 3. 伤害结算管线

攻击类伤害公式：

```text
最终伤害 = floor( (基础值 + 力量) × 虚弱0.75 × 易伤1.5 )
先扣格挡，溢出部分扣生命
```

- 全程浮点计算，最后向下取整一次；加法修正（力量）永远先于乘法修正；乘法先算攻击方钩子（虚弱）再算受击方钩子（易伤）。
- **多段攻击每一跳独立走完整管线**（含格挡吸收）。
- 伤害至少分三类，处理完全不同——当前用独立的 Action 类型区分（Attack / HP Loss 两条路径），荆棘等第三条路径出现时再抽统一的类型字段：

| 伤害类型 | 例子 | 受力量/虚弱/易伤修正 | 被格挡吸收 |
| --- | --- | --- | --- |
| Attack | 卡牌攻击、怪物攻击意图 | 是 | 是 |
| HP Loss | 中毒、卡牌自损 | 否 | 否 |
| Thorns | 荆棘反伤 | 否 | 是 |

- 格挡公式镜像：`floor((基础值 + 敏捷) × 脆弱0.75)`，但**只对打出卡牌直接获得的格挡成立**。金属化、镀层护甲、无惧疼痛、可塑、残像、遗物（奥利哈钢）、药水（格挡药水）、冰霜球的格挡不吃敏捷也不吃脆弱（wiki.gg Block：*Dexterity, Frail and No Block do not work with Relics, Potions or Orbs*；金属化页明确 *unaffected by Frail, Dexterity*）。把它写成「所有获得格挡」的总公式，金属化一进场就会错。

## 4. 牌堆区域与流转

原版只有四个区，**没有判定区/判定牌堆**：

```text
DrawPile（抽牌堆）→ Hand（手牌）→ DiscardPile（弃牌堆）
                              └→ ExhaustPile（消耗区，单向，本场战斗不再回来）
```

- 抽牌时抽牌堆空 → 弃牌堆洗入抽牌堆继续抽；两堆都空 → 停止抽牌，不是错误。
- 手牌上限 10。满手时的抽牌**失败**：牌留在抽牌堆，不抽出也不进弃牌堆（原版弹「手牌已满」提示）；「生成一张牌加入手牌」在满手时才落进弃牌堆。
- 消耗（Exhaust）是重要机制维度：一次性强力牌、诅咒/状态牌处理都靠它，Phase 2 引入。
- "延迟/下回合触发"类效果（如燃烧在回合结束结算）通过牌在手牌区挂结算逻辑或 Power 实现，不需要判定区。
- 会动牌堆的机制举例：检索（从抽牌堆**看见并选**牌，其余不洗、不改顺序）、头槌（Headbutt，把弃牌堆一张放到抽牌堆**顶**）、洗入随机位置（伤口、Alpha 的 Beta）、回声形态（复制打出的牌）。原版没有「塞到抽牌堆第 N 张」的牌；本项目容器若支持任意位置插入 / 取出，属于架构预留，不要写成原版已有。旧版此处写的「无头骑士」不是一代卡牌，应为头槌。

## 5. 目标选择

原版卡牌目标类型（1vN，无嘲讽机制，玩家自由选目标；敌方只有一个玩家可打，AI 不选目标）：

```text
SingleEnemy（单体指向）/ AllEnemies（全体）/ RandomEnemy（随机敌人）/ Self（自身）/ None（无目标）
```

## 6. Effect / Buff / Rule 的关系（本项目核心问题）

**事实：原版只有两层——Action（做事）和 Power（状态）。"Rule"不是原版的系统，而是 Power/Relic 的数值修改型钩子这一类用法。** 本项目把它独立成 RuleSystem 是自己的差异化设计，成立，但边界必须按"钩子的两种类型"来切：

| | EffectSystem | BuffSystem | RuleSystem |
| --- | --- | --- | --- |
| 回答的问题 | 发生了什么 | 谁身上有什么状态 | 公式此刻怎么算 |
| 生命周期 | 执行完即结束 | 有所有者/层数/时长 | 随来源（遗物、Buff）存在 |
| 能否改战斗状态 | 是（唯一改状态的层） | 否（只是数据容器） | 否（纯函数，入数值出数值） |
| 例子 | 造成 6 伤害、抽 2 张 | 中毒 5 层、力量 3 层 | 攻击伤害+力量层数、首回合能量+1 |

推论：

- **Buff 本身只是数据**（所有者 + 层数 + 生命周期）。"中毒每回合掉血"= Buff 定义引用的**触发器**（时机到了产生 Effect）；"力量加伤害"= Buff 定义引用的 **Rule**（参与数值计算）。一个 Buff 可以同时携带触发器和 Rule。
- **Rule 是纯函数**：输入（计算上下文，当前值），输出修改后的值，绝不直接执行战斗动作。这是 `.cursor/rules` 中"EffectSystem 做事 / RuleSystem 改规则"边界的机制化表述。
- **遗物 ≈ 无战斗生命周期的 Buff**：挂在角色（局外实体）身上，复用同一套触发器 + Rule，不需要第三套机制。

> **批注（Phase 2 设计复核补充）**：上一条只对"开战注入"类遗物成立（金刚杵开战给 1 力量，之后它确实就是一个普通 Buff）。纸鹤（虚弱 25%→40%）、钨条（失去生命少扣 1）、Snecko Skull（施加中毒 +1）整场常驻遗物列表、从不进任何生物的 Power 栏——它们复用的是**钩子接口的形状**，不是 Buff 容器本身；实现遗物时不要把这类遗物 `ApplyBuff` 进 Buff 字典。另外"修改 Buff"在原版拆成两类：改公式常数（纸鹤）是数值修改型钩子，对应本项目 RuleSystem；改某一次施加（Snecko Skull 加量、人工制品取消、冠军腰带追加）是 `ApplyPowerAction` 上的触发型钩子，不属于 Rule。与 Phase 2a/2b/2c 现有设计的逐条对照见 [`Phase 2 扩展边界批注.md`](Phase%202%20扩展边界批注.md)。

## 7. 会影响架构的特殊机制清单

Phase 2+ 设计时用这张表自查——不是要实现它们，而是架构不能堵死它们：

| 机制 | 原版例子 | 对架构的要求 |
| --- | --- | --- |
| 多段攻击 | 双持、旋风斩 | 伤害是可重复入队的 Action，每跳独立结算 |
| 触发链 | 荆棘反伤、遗物响应抽牌 | 队列必须支持执行中插入新 Action |
| 强制结束回合 | 时间吞噬者（打出 12 张牌强制结束回合） | "结束回合"是系统可触发的命令，不能只绑在 UI 按钮上 |
| 眩晕/打断 | 怪物被眩晕跳过行动 | 怪物执行意图前重新校验可行性 |
| 状态抵消 | 人工制品抵消下一个负面能力 | 施加 Buff 本身走可拦截的 Action |
| 改变回合规则 | 路障（格挡不清零）、冰淇淋（回合开始「当前能量 = 上限」换成「+= 上限」） | "回合开始清格挡"是可跳过的步骤，"重置能量"是可换算法的步骤；检查旗标即可，不需要规则引擎 |
| 伤害改写 | 无实体（受到的伤害改为 1；靴子在它之后把 1 抬回 5） | 伤害管线要有格挡前的 Final 阶段钩子，输出侧的靴子在格挡后 |
| 卡牌复制 | 回声形态 | "打出牌"要发事件，复制的是运行实体而非配置；第二遍也计入打出张数 |
| 运行时费用变化 | 本回合费用 -1 | 卡牌运行实体持有独立于配置的当前费用 |
| 多怪物时的批处理 | 中毒：全体怪物先清格挡再一起毒发，早于任何出手；金属化：各自出手之后 | 怪物侧"回合开始"是对全体的批处理，"回合结束"在出手之后，再加轮末减层；不要做成六个回调名 |
