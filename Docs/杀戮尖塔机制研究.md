# 杀戮尖塔机制研究（Phase 2+ 设计输入）

> **一句话结论：杀戮尖塔的底层不是"卡牌游戏"，而是"行动队列驱动的战斗模拟器"——一切改变战斗状态的事情都是排队执行的 Action；一切持续状态都是挂在生物身上的 Power，通过钩子在固定时机触发行为或修改数值。原版没有独立的 RuleSystem，本项目把"数值修改钩子"独立成 RuleSystem 属于自己的差异化设计。**

本文是对《杀戮尖塔》一代（Mod 社区对反编译源码的还原）与二代（官方 Godot 4 + C# 工程的反编译架构文档）实现机制的调研归纳，作为 Phase 2 及以后设计 ActionSystem / EffectSystem / BuffSystem / RuleSystem 时的事实依据。Phase 1 范围不受本文影响，见 [`Phase1-游戏设计.md`](Phase1-游戏设计.md)。

## 1. 官方实现架构

### 一代（Java + libGDX，Mod 社区还原）

四个支柱：

```text
AbstractGameAction  一次性行为（伤害、抽牌、施加能力…），进入 GameActionManager 队列按序执行
AbstractPower       持续状态（力量、中毒、易伤…），挂在生物的能力列表上，通过重写钩子生效
AbstractRelic       遗物，无独立机制，复用同一套钩子 + Action
AbstractCreature    生物（玩家/怪物公共基类），持有生命、格挡、Power 列表
```

关键机制：

- 卡牌的 `use()` 不直接改数据，而是 `addToBot(new DamageAction(...))` 把行为加入队列。
- Power 的钩子分两类，**这是理解 Effect/Buff/Rule 关系的钥匙**：
  1. **触发型钩子**：时机到了就做事，通常再入队新 Action。例：中毒在所有者回合开始入队一个扣血行为。
  2. **数值修改型钩子**：计算数值时被调用，返回修改后的值，不做任何事。例：力量的 `atDamageGive` 返回 `damage + 层数`。
- 施加、减层、移除 Power 本身也是 Action（`ApplyPowerAction` / `ReducePowerAction` / `RemovePowerAction`），因此人工制品才能"拦截下一个负面能力"——它拦的是队列里的施加行为。

### 二代（Godot 4 + C#，官方）

分层对我们最有参考价值：

```text
Model（不可变内容定义，ModelDb 统一注册）   → 对应本项目 ConfigSystem 的解析产物
Entity（Card/Creature/Player 运行实体）      → 对应本项目运行时状态
CombatState / RunState（局内/局外状态分离）  → 验证了局内外分离 + 进战斗时转换的思路
CombatManager / RunManager（流程控制）
GameActions（命令队列 + ActionExecutor，命令可网络序列化、可撤销）
Nodes（表现层，只消费状态）
seeded RNG（抽牌/地图/奖励各自独立的固定种子随机流）
History / Replay（时间戳事件日志驱动回放）
```

二代直接验证了本项目两个既定判断：局内/局外状态分离；配置定义到运行实体有一层显式转换（`CardData → CardDefinition` 同构）。

## 2. 回合时序（一代实测）

原文（[bakabird 的实测记录](https://www.cnblogs.com/bakabird/p/slaythesprite.html)）给出的是**四级**结算时机结构，而不是简单的"回合/轮"两级——这个区分只有在"一方有多个生物"（比如多个怪物）时才会体现出差异，本文之前的版本把它压扁成了两级，颗粒度不对，现按原文精度改写：

```text
回合行动开始 > 阵营行动开始 > 角色行动开始 > 角色行动结束 > 阵营行动结束 > 回合行动结束
```

一个"回合行动"（下文称"轮"，与 Phase 1 文档的"轮"对齐）= 玩家阵营行动一次 + 怪物阵营行动一次；"阵营行动"内部再按怪物阵营 A、B……各自的"角色行动"顺序展开——玩家阵营只有玩家一个生物，所以对玩家而言"阵营行动"与"角色行动"是同一时刻；只有多怪物场面才会区分出"怪物阵营整体开始"和"某只怪物自己的行动"两个不同时刻。

| 时机 | 发生的事 |
| --- | --- |
| 战斗开始 | 构建牌堆并洗牌；遗物战斗开始钩子；怪物决定首个意图 |
| 玩家阵营行动开始（= 玩家角色行动开始） | 玩家格挡清零（路障等例外）→ 回合开始钩子（含中毒结算）→ 能量重置为上限 → 抽 5 张 |
| 玩家角色行动中 | 打牌，每张牌展开为一串 Action 入队执行 |
| 玩家角色行动结束 | 回合结束钩子（金属化获得格挡等） |
| 玩家阵营行动结束 | 弃掉手牌（保留牌例外）→ 手牌中状态/诅咒牌结算（燃烧） |
| 怪物阵营行动开始 | **中毒在此刻统一结算**（不是每只怪物各自回合开始时分别结算,原文明确写"毒buff 在阵营行动开始时结算"） |
| 每只怪物的角色行动 | 该怪物格挡清零 → 执行意图 → 决定并展示下回合意图 |
| 轮结束（回合行动结束） | 易伤/虚弱/脆弱统一减 1 层；本轮刚施加的不减（justApplied 保护，保证至少完整生效一轮） |

要点：

- **格挡在"自己行动开始"清零**，不是行动结束——所以防御牌能挡住紧随其后的敌人攻击。Phase 1 游戏设计与此一致。
- **不同钩子的触发粒度不一样，不能假设统一**：中毒是"阵营级"钩子（多个怪物一起触发,不看各自回合），金属化是"角色级"钩子（只看该生物自己的行动结束）。Phase 2+ 设计 BuffSystem 触发器时，挂载点要能区分"阵营行动开始/结束"和"角色行动开始/结束"这两级，不能只留一个"回合开始/结束"的粗粒度接口——这对 Phase 1（单一敌人）不构成影响，但一旦引入多怪物就会暴露。
- **回合型 debuff 在轮（回合行动）结束统一减层**，不在各自阵营/角色行动内减。
- **怪物在自己行动结束就决定下回合意图**，玩家阵营行动全程可见，这是意图系统的本质：先斩后奏的反面。
- 能量默认不累积，玩家阵营行动开始直接重置（冰淇淋遗物例外）。

## 3. 伤害结算管线

攻击类伤害公式：

```text
最终伤害 = floor( (基础值 + 力量) × 虚弱0.75 × 易伤1.5 )
先扣格挡，溢出部分扣生命
```

- 全程浮点计算，最后向下取整一次；加法修正（力量）永远先于乘法修正；乘法先算攻击方钩子（虚弱）再算受击方钩子（易伤）。
- **多段攻击每一跳独立走完整管线**（含格挡吸收）。
- 伤害至少分三类，处理完全不同——当前用独立的 Action 类型区分（Attack / HP Loss 两条路径），荆棘等第三条路径出现时再抽统一的类型字段：

| 伤害类型 | 例子 | 受力量/虚弱/易伤修正 | 被格挡吸收 |
| --- | --- | --- | --- |
| Attack | 卡牌攻击、怪物攻击意图 | 是 | 是 |
| HP Loss | 中毒、卡牌自损 | 否 | 否 |
| Thorns | 荆棘反伤 | 否 | 是 |

- 格挡公式镜像：`floor((基础值 + 敏捷) × 脆弱0.75)`。

## 4. 牌堆区域与流转

原版只有四个区，**没有判定区/判定牌堆**：

```text
DrawPile（抽牌堆）→ Hand（手牌）→ DiscardPile（弃牌堆）
                              └→ ExhaustPile（消耗区，单向，本场战斗不再回来）
```

- 抽牌时抽牌堆空 → 弃牌堆洗入抽牌堆继续抽；两堆都空 → 停止抽牌，不是错误。
- 手牌上限 10（Phase 1 手牌恒 ≤5，不涉及；满手时的抽牌行为待实测再定）。
- 消耗（Exhaust）是重要机制维度：一次性强力牌、诅咒/状态牌处理都靠它，Phase 2 引入。
- "延迟/下回合触发"类效果（如燃烧在回合结束结算）通过牌在手牌区挂结算逻辑或 Power 实现，不需要判定区。
- 会动牌堆的机制举例：检索（从抽牌堆选牌）、无头骑士（把牌塞进抽牌堆指定位置）、回声形态（复制打出的牌）——所以牌堆容器要支持"任意位置插入/取出"，不能只暴露栈接口。

## 5. 目标选择

原版卡牌目标类型（1vN，无嘲讽机制，玩家自由选目标；敌方只有一个玩家可打，AI 不选目标）：

```text
SingleEnemy（单体指向）/ AllEnemies（全体）/ RandomEnemy（随机敌人）/ Self（自身）/ None（无目标）
```

## 6. Effect / Buff / Rule 的关系（本项目核心问题）

**事实：原版只有两层——Action（做事）和 Power（状态）。"Rule"不是原版的系统，而是 Power/Relic 的数值修改型钩子这一类用法。** 本项目把它独立成 RuleSystem 是自己的差异化设计，成立，但边界必须按"钩子的两种类型"来切：

| | EffectSystem | BuffSystem | RuleSystem |
| --- | --- | --- | --- |
| 回答的问题 | 发生了什么 | 谁身上有什么状态 | 公式此刻怎么算 |
| 生命周期 | 执行完即结束 | 有所有者/层数/时长 | 随来源（遗物、Buff）存在 |
| 能否改战斗状态 | 是（唯一改状态的层） | 否（只是数据容器） | 否（纯函数，入数值出数值） |
| 例子 | 造成 6 伤害、抽 2 张 | 中毒 5 层、力量 3 层 | 攻击伤害+力量层数、首回合能量+1 |

推论：

- **Buff 本身只是数据**（所有者 + 层数 + 生命周期）。"中毒每回合掉血"= Buff 定义引用的**触发器**（时机到了产生 Effect）；"力量加伤害"= Buff 定义引用的 **Rule**（参与数值计算）。一个 Buff 可以同时携带触发器和 Rule。
- **Rule 是纯函数**：输入（计算上下文，当前值），输出修改后的值，绝不直接执行战斗动作。这是 `.cursor/rules` 中"EffectSystem 做事 / RuleSystem 改规则"边界的机制化表述。
- **遗物 ≈ 无战斗生命周期的 Buff**：挂在角色（局外实体）身上，复用同一套触发器 + Rule，不需要第三套机制。

> **批注（Phase 2 设计复核补充）**：上一条只对"开战注入"类遗物成立（金刚杵开战给 1 力量，之后它确实就是一个普通 Buff）。纸鹤（虚弱 25%→40%）、钨条（失去生命少扣 1）、Snecko Skull（施加中毒 +1）整场常驻遗物列表、从不进任何生物的 Power 栏——它们复用的是**钩子接口的形状**，不是 Buff 容器本身；实现遗物时不要把这类遗物 `ApplyBuff` 进 Buff 字典。另外"修改 Buff"在原版拆成两类：改公式常数（纸鹤）是数值修改型钩子，对应本项目 RuleSystem；改某一次施加（Snecko Skull 加量、人工制品取消、冠军腰带追加）是 `ApplyPowerAction` 上的触发型钩子，不属于 Rule。与 Phase 2a/2b/2c 现有设计的逐条对照见 [`Phase 2 扩展边界批注.md`](Phase%202%20扩展边界批注.md)。

## 7. 会影响架构的特殊机制清单

Phase 2+ 设计时用这张表自查——不是要实现它们，而是架构不能堵死它们：

| 机制 | 原版例子 | 对架构的要求 |
| --- | --- | --- |
| 多段攻击 | 双持、旋风斩 | 伤害是可重复入队的 Action，每跳独立结算 |
| 触发链 | 荆棘反伤、遗物响应抽牌 | 队列必须支持执行中插入新 Action |
| 强制结束回合 | 时间吞噬者（打出 12 张牌强制结束回合） | "结束回合"是系统可触发的命令，不能只绑在 UI 按钮上 |
| 眩晕/打断 | 怪物被眩晕跳过行动 | 怪物执行意图前重新校验可行性 |
| 状态抵消 | 人工制品抵消下一个负面能力 | 施加 Buff 本身走可拦截的 Action |
| 改变回合规则 | 路障（格挡不清零）、冰淇淋（能量保留） | "回合开始清格挡/重置能量"也是可被 Rule 修改的规则 |
| 伤害改写 | 无实体（受到的伤害改为 1） | 伤害管线要有 Final 阶段钩子 |
| 卡牌复制 | 回声形态 | "打出牌"要发事件，复制的是运行实体而非配置 |
| 运行时费用变化 | 本回合费用 -1 | 卡牌运行实体持有独立于配置的当前费用 |
| 多怪物时的钩子粒度差异 | 中毒（阵营级，见第 2 节）vs 金属化（角色级） | 触发器要能挂在"阵营行动开始/结束"和"角色行动开始/结束"两级时机点，不能只留一个粗粒度的"回合开始/结束" |

## 8. 对本项目的映射

| 研究结论 | 对应本项目 | 引入时机 |
| --- | --- | --- |
| 命令式 API + 状态唯一写入口 | `BattleSession`（已定） | Phase 1 |
| Model → Entity 转换 | `CardData → CardDefinition`（已定） | Phase 1 |
| 固定种子随机 | 注入 `System.Random`（已定） | Phase 1 |
| Action 队列 | ActionSystem | Phase 2，与 EffectSystem 同期——组合效果、触发链是队列的第一批真实客户 |
| Power 钩子二分 | BuffSystem（数据）+ 触发器（产生 Effect）+ RuleSystem（改数值） | Phase 2 |
| 伤害类型区分 | EffectSystem 的 DamageInfo | Phase 2 |
| 消耗区 ExhaustPile | CardSystem | Phase 2+ |
| 局内/局外状态分离 | `BattleSession` 已隔离，局外系统后续以"构造时传入数据"对接 | Phase 3+ |
| 事件日志驱动回放 | ReplaySystem | V1.1 |
