# Phase 2c 技术设计：RuleSystem（伤害计算规则）

> **技术目标：Rule 是纯函数——输入伤害上下文，输出修改后的数值，绝不直接执行战斗动作。规则集合固定写死在计算器内部，不做注册引擎。**
>
> 这是全部三个子阶段里唯一直接修改 Phase 2a 已有类（`DamageAction`）的一步，改动范围要控制到最小。

## 1. 技术原则

延续 Phase 1/2a/2b 的优先级：**正确性 > 可测试性 > 可读性 > 当前已知需求的扩展性**。补充：

- `IDamageRule` 只有一个方法、一种形状，不区分"加法规则接口"和"乘法规则接口"——加法/乘法只是 `DamageCalculator` 内部两个执行阶段的分类，不是类型系统层面的区分。
- 规则实例是无状态的（`StrengthDamageRule` 等都可以是单例），真正的状态（层数）在 `CombatantState` 的 Buff 容器里，规则只读取。
- 不做规则的外部注册接口（比如 `RuleRegistry.Register(...)`）：当前只有 3 条规则，注册机制没有第二个调用方，加了也用不上。

## 2. 分层与依赖

```text
Core.Actions（DamageAction：改造为持有 source，Execute 内部调用 DamageCalculator）
  ↓
Core.Rules（新增：DamageContext / IDamageRule / StrengthDamageRule / WeakDamageRule / VulnerableDamageRule / DamageCalculator）
  ↓
Core.Combatants（CombatantState：只读取 GetBuffStacks/HasBuff，Phase 2b 已提供，本阶段不改）
  ↓
Core.Effects（DamageEffect：不变，仍然只负责把最终数值应用到目标）
```

依赖约束新增：

- `Core.Rules` 不引用 `Core.Actions`、`Core.Effects`：规则只关心数值，不知道自己被谁调用、算完之后数值去了哪里。
- `Core.Actions` 依赖 `Core.Rules`（`DamageAction` 需要调用 `DamageCalculator`），方向不能反过来。

## 4. 核心接口

### DamageContext / IDamageRule

```csharp
namespace CardRPGFramework.Core.Rules
{
    // Damage 全程用 double 运算，只在最终结果读取时取整一次，
    // 对齐研究文档"全程浮点计算、最后向下取整一次"，避免乘法规则多次叠加时因为
    // 中间取整导致结果和"一次性算完再取整"不一致。
    public sealed class DamageContext
    {
        public double Damage { get; set; }
        public CombatantState Source { get; }
        public CombatantState Target { get; }

        public DamageContext(int baseDamage, CombatantState source, CombatantState target)
        {
            Damage = baseDamage;
            Source = source;
            Target = target;
        }
    }

    // 规则是纯函数：只读 Source/Target 上的 Buff 数据，只写 Damage，不调用任何 Effect/Action。
    public interface IDamageRule
    {
        void Apply(DamageContext context);
    }
}
```

### 三条具体规则

```csharp
namespace CardRPGFramework.Core.Rules
{
    public sealed class StrengthDamageRule : IDamageRule
    {
        public void Apply(DamageContext context) => context.Damage += context.Source.GetBuffStacks("strength");
    }

    public sealed class WeakDamageRule : IDamageRule
    {
        public void Apply(DamageContext context)
        {
            if (context.Source.HasBuff("weak")) context.Damage *= 0.75;
        }
    }

    public sealed class VulnerableDamageRule : IDamageRule
    {
        public void Apply(DamageContext context)
        {
            if (context.Target.HasBuff("vulnerable")) context.Damage *= 1.5;
        }
    }
}
```

### WeakBuff / VulnerableBuff（规则读取的数据来源）

```csharp
namespace CardRPGFramework.Core.Buffs
{
    // 与 StrengthBuff 同形：只存层数，不实现 IBuffTrigger。
    // Id 字符串必须与 WeakDamageRule / VulnerableDamageRule 里读取的一致，
    // 这是本阶段唯一一处"字符串约定"，改一边就要同步改另一边。
    public sealed class WeakBuff : BuffState
    {
        public override string Id => "weak";
        public WeakBuff(int stacks) : base(stacks) { }
    }

    public sealed class VulnerableBuff : BuffState
    {
        public override string Id => "vulnerable";
        public VulnerableBuff(int stacks) : base(stacks) { }
    }
}
```

没有这两个类，`HasBuff("weak")`/`HasBuff("vulnerable")` 永远为 false，规则写对了也测不出效果。

### DamageCalculator（固定两段管线，不做注册引擎）

```csharp
namespace CardRPGFramework.Core.Rules
{
    public static class DamageCalculator
    {
        private static readonly IReadOnlyList<IDamageRule> AdditiveRules = new IDamageRule[] { new StrengthDamageRule() };
        private static readonly IReadOnlyList<IDamageRule> MultiplicativeRules = new IDamageRule[] { new WeakDamageRule(), new VulnerableDamageRule() };

        public static int CalculateFinalDamage(DamageContext context)
        {
            foreach (var rule in AdditiveRules) rule.Apply(context);
            foreach (var rule in MultiplicativeRules) rule.Apply(context);
            return (int)Math.Floor(context.Damage);
        }
    }
}
```

### DamageAction 改造

```csharp
namespace CardRPGFramework.Core.Actions
{
    public sealed class DamageAction : IAction
    {
        private readonly CombatantState _source;
        private readonly CombatantState _target;
        private readonly int _baseAmount;

        public DamageAction(CombatantState source, CombatantState target, int baseAmount)
        {
            _source = source;
            _target = target;
            _baseAmount = baseAmount;
        }

        public void Execute(ActionContext context)
        {
            var damageContext = new DamageContext(_baseAmount, _source, _target);
            var finalDamage = DamageCalculator.CalculateFinalDamage(damageContext);
            DamageEffect.Apply(_target, finalDamage);
        }
    }
}
```

`DamageEffect.Apply` 本身不改——它接收的还是一个 `int` 最终数值，不知道这个数值是怎么算出来的，Phase 2a 埋的分层在这里生效。

## 5. BattleSession 改动

`EnqueueCardAction` 里 `CardType.Attack` 分支新增 `source` 参数，并照 Phase 2b 的剧毒分支新增两张 Buff 卡的接线：

```csharp
case CardType.Attack: _actionQueue.Enqueue(new DamageAction(Player, Enemy, card.Value)); break;
case CardType.Weak: _actionQueue.Enqueue(new ApplyBuffAction(Player, Enemy, new WeakBuff(card.Value))); break;
case CardType.Vulnerable: _actionQueue.Enqueue(new ApplyBuffAction(Player, Enemy, new VulnerableBuff(card.Value))); break;
```

两张卡的目标都是 `Enemy`：虚弱打在敌人身上，降低的是敌人的攻击（规则读的是攻击发起方），不要照力量卡抄成 `(Player, Player, ...)`，那样会做出一张削弱自己的废卡。

敌人固定攻击原来是直接调用 `Player.TakeDamage(EnemyDamage)`，跳过了整个 Action/Effect/Rule 管线。本阶段统一改成：

```csharp
_actionQueue.Enqueue(new DamageAction(Enemy, Player, EnemyDamage));
_actionQueue.RunAll(new ActionContext(_actionQueue));
```

插入位置就是原来 `Player.TakeDamage(EnemyDamage)` 那一行，即 `TriggerTurnStartBuffs(Enemy)` 与 `Enemy.IsDead` 胜利判定**之后**。中毒结算和敌人攻击必须是两次独立的 `RunAll`：不要把 `DamageAction` 提前入队合并进中毒那次 `RunAll`，否则毒杀敌人之后这一下攻击仍会打出去，Phase 2b 的 `PoisonKillsEnemy_EndsBattleInVictory_WithoutEnemyAttack` 会失败。

这不是"顺便重构"——一旦 `DamageAction` 需要 `source` 才能工作，敌人攻击如果继续绕过它，规则系统就只对玩家生效、对敌人不生效，这是不一致的架构状态，必须在引入 Rule 的同一阶段修正，不能拖到以后。

## 6. 测试策略

- `Core.Rules` 新增测试：三条规则单独验证（力量加算正确；虚弱只在 Source 有虚弱时生效，且 2 层与 1 层结果相同；易伤只在 Target 有易伤时生效）；`DamageCalculator` 验证组合场景下的结算顺序和取整时机。取整用例必须选"中间取整会算错"的组合：基础 5 + Source 虚弱 + Target 易伤 → `floor(5 × 0.75 × 1.5) = floor(5.625) = 5`，若虚弱后先取整再乘易伤会得到 `floor(floor(3.75) × 1.5) = 4`。`floor((6+3) × 1.5) = 13` 这种两种算法答案相同的数不能当唯一的组合用例。
- `BattleSessionTests` 新增：玩家带力量时攻击伤害提高、敌人带易伤时玩家攻击伤害提高、敌人带虚弱时敌人固定攻击降低（6 → 4）；玩家带虚弱时攻击伤害降低（直接 `Player.ApplyBuff(new WeakBuff(1))` 构造，对局里没有这个来源，不必为它做卡）；敌人固定攻击在没有任何 Buff 时数值与 Phase 1 完全一致（回归测试，证明迁移到 Action 管线没有引入偏差）。
- 既有 `ActionQueueTests` 里 `DamageAction` 的两参数构造改为三参数（source 给一个无 Buff 的 `CombatantState` 即可），**只改构造，不改断言数值**——TODO 里"遗留测试无需修改断言"指的是数字，不是指编译能直接过。
- 确认中毒（`HpLossAction`）路径完全没有被本阶段改动触及，Phase 2b 的中毒测试无需修改即可通过。

## 7. 排除项

- 不做规则注册/配置化接口。
- 不做除力量/虚弱/易伤外的第 4 条规则或占位接口。
- 不做暴击、闪避、护甲穿透等研究文档提到但当前没有卡牌需要的机制。
- 不修改格挡（`BlockEffect`）或治疗（`HealEffect`）的计算方式，规则只作用于 Attack 类型伤害。

## 8. 关键技术决策

| 决策 | Phase 2c 选择 | 原因 |
| --- | --- | --- |
| `IDamageRule` 接口形状 | 单一接口，直接改写 `DamageContext.Damage` | 加法/乘法只是执行阶段分类，不需要类型层面区分 |
| 规则集合来源 | 硬编码在 `DamageCalculator` 内部 | 只有 3 条规则，注册引擎没有第二个消费场景 |
| 数值精度 | `DamageContext.Damage` 用 `double`，最后统一 `Math.Floor` | 对齐研究文档，避免多次乘法规则中间取整导致结果偏差 |
| 敌人攻击是否接入同一管线 | 接入 | 否则规则系统只对玩家生效，架构状态不一致 |
| 是否给 Rule 传入完整 `BattleSession` | 不传，只传 `DamageContext`（含 Source/Target） | 规则目前只需要读 Buff 数据，传更多上下文没有消费场景 |

## 10. 扩展边界批注（非本阶段范围）

> - `WeakDamageRule` 按"有无"乘 0.75 而不按层数，与原版一致（虚弱层数是持续回合数，不是强度）；以后引入轮末减层时不要改成按层数放大倍率。
> - 管线止于取整后交给 `DamageEffect`，而原版在这之后还有三个**互不相同**的挂钩点，都不是往 `AdditiveRules`/`MultiplicativeRules` 里加规则能解决的：无实体"受到的伤害改为 1"在**格挡前**的 Final 修正（`DamageAction` 与 `HpLossAction` 两条路径都要经过）；鸟居"未被格挡的攻击伤害 ≤5 时变 1"在**格挡后、仅 Attack**；钨条"失去生命少扣 1"在 `LoseHp` 前（Phase 2b 已把 `LoseHp` 定为唯一生命减少入口）。时机地图见扩展边界批注第 2 节。
> - `DamageContext` 只能读交战双方身上的 Buff；纸鹤（虚弱 25%→40%）这类遗物出现时，Context 需要能读到"本场持有的遗物"——届时改的是虚弱倍率这个参数，不是再乘一层伤害。
>
