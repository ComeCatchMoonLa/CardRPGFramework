# Phase 2a 技术设计：ActionSystem + EffectSystem

> **技术目标：让"卡牌做什么"（Action）和"状态怎么被改"（Effect）成为两个独立、可分别测试的层，为 Phase 2b 的 Buff 触发和 Phase 2c 的伤害规则预留插入点。**
>
> 只解决当前已确定的插入点需求，不为假设中的未来需求（多目标、异步执行、事件总线）预先设计接口。

## 1. 技术原则

延续 [`Docs/Phase 1/技术设计.md`](../Phase%201/技术设计.md) 第 1 节的优先级：**正确性 > 可测试性 > 可读性 > 当前已知需求的扩展性**。补充两条本阶段专用原则：

- Action 的种类只对应"当前已经存在的效果"，不为假设中的效果预留组合能力（不做 `CompositeAction`/`ConditionalAction`/`DelayedAction`/`RepeatAction`/`SequenceAction`）。
- Effect 只负责状态修改，不做任何数值计算；数值怎么算是 Action（本阶段）和 Rule（Phase 2c）的职责，不能让 Effect 反过来知道"是谁在算它的数值"。

## 2. 分层与依赖

```text
Controllers（BattleController）
  ↓
Core.Battle（BattleSession：持有 ActionQueue，把卡牌类型翻译成具体 Action 并驱动执行）
  ↓
Core.Actions（IAction / ActionQueue / ActionContext：只知道"排队"和"执行"，不知道具体效果内容）
  ↓
Core.Effects（DamageEffect / BlockEffect / HealEffect：只知道"怎么改 CombatantState"，不知道谁调用了它）
  ↓
Core.Combatants（CombatantState：不变）
```

依赖约束新增：

- `Core.Actions` 不引用 `Core.Effects`（Action 类可以引用 Effect，方向是 Actions → Effects，反过来不行）。
- `Core.Effects` 不引用 `Core.Actions`、`Core.Battle`：Effect 是最底层，只依赖 `Core.Combatants`。
- `BattleSession` 是唯一持有 `ActionQueue` 实例的地方，Views/Controllers 不直接接触 Action/Effect。

## 4. 核心接口

### ActionContext / IAction / ActionQueue

```csharp
namespace CardRPGFramework.Core.Actions
{
    // 携带 Action 执行时可能需要的上下文；现在只放 Queue，
    // 预留 Battle 引用是因为 Phase 2b 的中毒触发需要拿到"当前回合"的信息，
    // 不是现在就要用它——字段先声明，用不到就不塞值。
    public sealed class ActionContext
    {
        public ActionQueue Queue { get; }

        public ActionContext(ActionQueue queue)
        {
            Queue = queue;
        }
    }

    public interface IAction
    {
        void Execute(ActionContext context);
    }

    // FIFO 队列。RunAll 执行期间，Action.Execute 内部可以继续调用 context.Queue.Enqueue，
    // 这是 Phase 2b 中毒触发追加伤害 Action 时需要的能力。不支持插队/优先级。
    public sealed class ActionQueue
    {
        private readonly Queue<IAction> _pending = new();

        public void Enqueue(IAction action) => _pending.Enqueue(action);

        public void RunAll(ActionContext context)
        {
            while (_pending.Count > 0)
            {
                _pending.Dequeue().Execute(context);
            }
        }
    }
}
```

> 当前实现假设 `Execute` 不抛异常，`RunAll` 没有做异常时清空剩余队列的处理；这是"当前 MVP 保证同步无异常路径"的已知边界，不是遗漏——真正商业项目会在这里加异常隔离和 Action 生命周期管理，但当前所有 Action 都是无副作用的纯状态修改，加异常处理没有对应的失败场景可以测试，先不做。

### 具体 Action（与 Phase 1 三种卡牌效果一一对应）

```csharp
namespace CardRPGFramework.Core.Actions
{
    public sealed class DamageAction : IAction
    {
        private readonly CombatantState _target;
        private readonly int _amount;

        public DamageAction(CombatantState target, int amount)
        {
            _target = target;
            _amount = amount;
        }

        public void Execute(ActionContext context) => DamageEffect.Apply(_target, _amount);
    }

    // BlockAction、HealAction 结构相同，分别调用 BlockEffect.Apply / HealEffect.Apply。
}
```

> Phase 2c 会修改 `DamageAction`：新增 `source` 字段，`Execute` 内部改为先构造 `DamageContext` 交给 `DamageCalculator` 算出最终伤害，再调用 `DamageEffect.Apply`。本阶段不提前加这个字段——加了也没有消费者，属于过度设计。

### Effect（纯状态修改，不做计算）

```csharp
namespace CardRPGFramework.Core.Effects
{
    public static class DamageEffect
    {
        public static void Apply(CombatantState target, int amount) => target.TakeDamage(amount);
    }

    public static class BlockEffect
    {
        public static void Apply(CombatantState target, int amount) => target.GainBlock(amount);
    }

    public static class HealEffect
    {
        public static void Apply(CombatantState target, int amount) => target.Heal(amount);
    }
}
```

Effect 目前只是对 `CombatantState` 现有方法的一层转发，看起来"多余"，但这一层是 Phase 2c 伤害规则的必要插入点（`DamageAction` 算完最终伤害后仍然调用同一个 `DamageEffect.Apply`，`Effect` 本身不用改）。不用接口（`IEffect`）统一它们，因为三个 Effect 之间没有共同的多态调用点——`BattleSession`/Action 从来不会"随便拿一个 Effect 执行"，都是各自 Action 类型精确知道自己该调用哪个 Effect。

## 5. BattleSession 迁移方式

`BattleSession` 新增一个 `ActionQueue` 字段，构造时创建，生命周期跟 `BattleSession` 一致（不是每次 `TryPlayCard` 新建一个，因为 Phase 2b 需要队列在整场战斗内持续存在，以便回合开始/结束时的 Buff 触发也能复用同一个队列）。

改造前（Phase 1）：

```csharp
private void ResolveCard(CardDefinition card)
{
    switch (card.Type)
    {
        case CardType.Attack: Enemy.TakeDamage(card.Value); break;
        case CardType.Defend: Player.GainBlock(card.Value); break;
        case CardType.Heal: Player.Heal(card.Value); break;
    }
}
```

改造后（Phase 2a）：

```csharp
private void EnqueueCardAction(CardDefinition card)
{
    switch (card.Type)
    {
        case CardType.Attack: _actionQueue.Enqueue(new DamageAction(Enemy, card.Value)); break;
        case CardType.Defend: _actionQueue.Enqueue(new BlockAction(Player, card.Value)); break;
        case CardType.Heal: _actionQueue.Enqueue(new HealAction(Player, card.Value)); break;
    }
}
```

`TryPlayCard` 里原来调用 `ResolveCard(card)` 的位置，改成：

```csharp
EnqueueCardAction(card);
_actionQueue.RunAll(new ActionContext(_actionQueue));
```

`switch(CardType)` 依然存在——它现在决定的是"该入队哪个 Action"，不是"直接怎么改状态"，这是本阶段唯一保留分支判断的地方，符合游戏设计文档"只重构怎么执行，不碰是什么"的边界。

## 6. 测试策略

在现有 `BattleSessionTests.cs` 之外新增：

- Action/Effect 独立单元测试：`DamageAction` 执行后目标扣血、`ActionQueue.RunAll` 按入队顺序执行、队列执行中追加的 Action 会在同一次 `RunAll` 内被处理完。
- `BattleSessionTests.cs` 里原有的攻击/防御/治疗测试保持不变（断言的是 `Player`/`Enemy` 的最终状态，不关心中间是否经过 Action），用于证明重构没有改变外部行为。

## 7. 排除项

- 不做 `CompositeAction`（组合多个 Action 顺序执行）、`ConditionalAction`（按条件决定是否执行）、`DelayedAction`（延迟 N 回合执行）、`RepeatAction`（重复执行）、`SequenceAction`——这些是商业项目的需求，当前没有任何一张卡牌需要它们。
- 不引入多线程/协程执行 Action，`RunAll` 在当前调用栈内同步跑完整个队列，和 Phase 1 的同步结算模型一致。
- 不引入事件总线通知 Action 执行结果，`Views` 仍然按 Phase 1 的方式在命令返回后主动读取 `BattleController` 状态刷新。

## 8. 关键技术决策

| 决策 | Phase 2a 选择 | 原因 |
| --- | --- | --- |
| Action 与 Effect 是否分层 | 分层 | Effect 是 Phase 2c 伤害规则的插入点，现在分好成本极低 |
| Effect 是否用统一接口 `IEffect` | 不用 | 没有任何调用点需要多态调用 Effect，加接口没有消费者 |
| ActionQueue 生命周期 | 跟随 `BattleSession`，贯穿整场战斗 | Phase 2b 回合级 Buff 触发需要复用同一个队列 |
| Action 是否支持插队/优先级 | 不支持，纯 FIFO | 当前没有任何机制需要打断已入队的 Action |
| 队列执行方式 | 同步、当前调用栈内跑完 | 没有动画等待或异步需求，和 Phase 1 结算模型一致 |

- `Core.Actions`、`Core.Effects` 不引用 `UnityEngine`，与 `Core.Battle`/`Core.Combatants`/`Core.Cards` 保持相同的纯 C# 约束。

## 10. 扩展边界批注（非本阶段范围）
