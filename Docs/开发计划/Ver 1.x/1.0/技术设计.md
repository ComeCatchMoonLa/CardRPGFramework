# 1.0 技术设计：`RunState`

> **技术目标：新增 `Core.Run`。** `RunState` 持有一局局外状态，输出 `BattleInput`、接收 `ApplyResult`、提供 `AddCard`。`BattleSetup` 增加当前生命（第四参默认 = 最大生命），`CombatantState` / `BattleSession` 允许残血开战。Session 构造函数其余签名不变。无 UI、无 `RunConfig` SO。Play 仍是 `TestScene` + `BattleConfig`。
>
> 玩法要求见 [`游戏设计.md`](游戏设计.md)，执行顺序见 [`TODO.md`](TODO.md)。短 Run 总设计见 [`../游戏设计.md`](../游戏设计.md)。

## 1. 技术原则

延续 0.1～0.7 的优先级：**正确性 > 可测试性 > 可读性 > 当前已知需求的扩展性**。补充：

- **Run 不创建战斗。** `CreateBattleInput` 返回 `BattleInput`，里面没有 `BattleSession`。谁 `new Session` 是调用方的事：本版是测试辅助，1.1 是 `BattleController.Begin`。
- **进战斗是快照，出战斗只写约定的两个数。** `ApplyResult` 只收 `won` 与 `remainingHp`。牌组、消耗、弃牌、Buff、格挡都不写回。
- **拒绝，不静默。** 同一节点第二次 `ApplyResult`、失败或通关后再要战斗输入，都抛 `InvalidOperationException`、状态不变。第二次胜利若当 no-op，`nodeIndex` 会偷偷 +2，测试也抓不住。
- **不引用 `UnityEngine` / `Core.Actions`。** `Core.Run` 可以引用 `Core.Battle`（`BattleSetup`）、`Core.Cards`、`Core.Enemies`、`Core.Relics`。

## 4. 核心接口

### 4.1 BattleSetup 与 CombatantState

```csharp
public readonly struct BattleSetup
{
    public int PlayerMaxHp { get; }
    public int EnergyPerTurn { get; }
    public int HandSize { get; }
    public int PlayerCurrentHp { get; }

    public BattleSetup(int playerMaxHp, int energyPerTurn, int handSize)
        : this(playerMaxHp, energyPerTurn, handSize, playerMaxHp) { }

    /// current 必须 > 0 且 ≤ max，否则 ArgumentOutOfRangeException。
    public BattleSetup(int playerMaxHp, int energyPerTurn, int handSize, int playerCurrentHp);
}

public sealed class CombatantState
{
    public CombatantState(int maxHp) : this(maxHp, maxHp) { }

    /// currentHp 必须 > 0 且 ≤ maxHp。开战残血走这一条；0 血是死亡，不是合法开局。
    public CombatantState(int maxHp, int currentHp);
}
```

**[已定] 三参 / 四参两个重载，不要用 `< 0` 当未传哨兵。** 现有 `new BattleSetup(hp, energy, hand)` 与 `BattleConfig.ToSetup()` 走三参，当前生命 = 最大生命。显式传入 `0`、负数、`> max` 一律抛——和 `CombatantState(max, current)` 同一条边界，避免 `new BattleSetup(80, 3, 5, -5)` 静默成满血。不要用 `int?`。

**[已定] Session 构造函数其余签名不变**：`(setup, enemy, deck, random, relics = null)`。内部 `Player = new CombatantState(setup.PlayerMaxHp, setup.PlayerCurrentHp)`。敌人仍满血。

### 4.2 BattleInput

```csharp
namespace CardRPGFramework.Core.Run
{
    /// CreateBattleInput 的返回值。五个字段，不是"随便一个包"。
    public sealed class BattleInput
    {
        public BattleSetup Setup { get; }
        public IReadOnlyList<CardDefinition> Deck { get; }
        public IReadOnlyList<RelicState> Relics { get; }
        public EnemyDefinition Enemy { get; }
        public Random Random { get; }

        public BattleInput(BattleSetup setup, IReadOnlyList<CardDefinition> deck,
            IReadOnlyList<RelicState> relics, EnemyDefinition enemy, Random random);
    }
}
```

**[已定] 五个字段：**

| 字段 | 内容 |
| --- | --- |
| `Setup` | 含当前生命的玩家标量。牌组 / 遗物 / 敌人不塞进 Setup |
| `Deck` | Run 牌组的**浅拷贝**（`CardDefinition` 引用列表；定义不可变）。调用方再交给 `CardPile` 不会改到 Run 那份列表 |
| `Relics` | 每个 Id 当场 `RelicFactory.Create` 的**新实例**。开战钩子（金刚杵）每场都会再打一次；不复用上一场挂在 `CombatantState` 上的对象 |
| `Enemy` | 当前 `nodeIndex` 对应的那份 `EnemyDefinition`（开局传入的引用，不拷贝内部） |
| `Random` | `new Random(f(runSeed, nodeIndex))`，**所有权交给调用方**。`RunState` 不持有、用完即弃 |

`CreateBattleInput` 可以对本节点调用多次，每次 `new Random(同一 f(runSeed, nodeIndex))`，**不**推进节点。两次输入的 `Setup` / 牌组内容与顺序 / 敌人相同，`Random` 是两个独立实例、同一种子。

**[已定] `CreateBattleInput` 不洗牌、不调用 `Random.Next`。** 返回的 `Deck` 是 Run 牌组的浅拷贝，顺序与 Run 里那份相同。洗牌发生在调用方把 `Deck` + `Random` 交给 `CardPile` 构造之时。若在 Run 里先 `Next()`，同节点两次输入的对照会红。

**[已定] 战斗种子。** `f(runSeed, nodeIndex) = unchecked(runSeed * 397 ^ nodeIndex)`。不使用 `HashCode.Combine`（跨进程 / 运行时版本不保证稳定）。测试可以按这个公式自算期望种子。

### 4.3 RunState

```csharp
namespace CardRPGFramework.Core.Run
{
    public sealed class RunState
    {
        public int RunSeed { get; }
        public int MaxHp { get; }
        public int CurrentHp { get; private set; }
        public int EnergyPerTurn { get; }
        public int HandSize { get; }
        public int Gold { get; }                  // 恒 0
        public int NodeIndex { get; private set; }
        public IReadOnlyList<CardDefinition> Deck { get; }
        public IReadOnlyList<string> RelicIds { get; }
        public bool IsFailed { get; private set; }
        public bool IsCleared => !IsFailed && NodeIndex >= _encounters.Count;
        public bool IsOver => IsFailed || IsCleared;

        /// playerSetup 提供 MaxHp / EnergyPerTurn / HandSize / 开局当前生命（通常 = Max）。
        /// deck / relicIds / encounters 均拷贝列表。encounters 必须恰好 3 条、无 null。
        /// relicIds 允许空列表，null 抛；非空则无重复且 RelicFactory.IsKnown。deck 非 null，允许空列表（测试）。
        public RunState(int runSeed, BattleSetup playerSetup,
            IReadOnlyList<CardDefinition> deck, IReadOnlyList<string> relicIds,
            IReadOnlyList<EnemyDefinition> encounters);

        public BattleInput CreateBattleInput();
        public void ApplyResult(bool won, int remainingHp);
        public void AddCard(CardDefinition card);
    }
}
```

构造拷贝 `deck` / `relicIds` / `encounters` 三份列表（浅拷贝元素）。`Gold` 没有 setter。参数恰好 5 个：种子、玩家标量、牌组、遗物 Id、三场敌人。`IsCleared` 用 `_encounters.Count`（本版恰好 3），不要另设常量 3。

`CreateBattleInput`：`IsOver` 时抛 `InvalidOperationException`。否则按 4.2 组 `BattleInput`。通关后再要输入继续抛。

**[已定] `AddCard` 只在失败或 `card == null` 时拒绝。** `card == null` 抛 `ArgumentNullException`；`IsFailed` 抛 `InvalidOperationException`。`IsCleared` 后仍允许追加——第三场胜利先 `ApplyResult` 写回（`nodeIndex` 到表末、顶栏才能显示残血），1.3 的奖励页还要加卡。不要把 `IsOver` 当成牌组冻结。1.3 才抽三张，本版测试直接调。

### 4.4 ApplyResult：拒绝，不静默

**[已定] 状态机。** `ApplyResult` 只接受「当前节点已经 `CreateBattleInput` 过、且尚未写过结果」。胜利后 `nodeIndex++`，必须再 `CreateBattleInput` 才能写下一场——否则第二次胜利会落在新下标上，`nodeIndex` 偷偷 +2。

| 当前状态 | 调用 | 结果 |
| --- | --- | --- |
| 未结束，本节点已 `CreateBattleInput`、还没写过结果，`won == true`，`0 < remainingHp ≤ MaxHp` | 胜利 | 写 `CurrentHp = remainingHp`，`nodeIndex++`。`NodeIndex >= _encounters.Count` 即为通关（本版 Count 为 3，不要写成魔法 `== 3`） |
| 未结束，本节点已 `CreateBattleInput`、还没写过结果，`won == false` | 失败 | 标 `IsFailed = true`；不写生命、不推进 `nodeIndex` |
| `won == true` 且 `remainingHp <= 0` | 调用错误 | 抛 `ArgumentOutOfRangeException`（失败走 `won: false`，不要用胜利 + 0 血表示死亡） |
| `won == true` 且 `remainingHp > MaxHp` | 调用错误 | 抛 `ArgumentOutOfRangeException` |
| 已失败、已打完三场、本节点已经 `ApplyResult` 过、或本节点还没 `CreateBattleInput` | 任何 `ApplyResult` | 抛 `InvalidOperationException`，状态不变 |
| 失败或通关后 | `CreateBattleInput` | 抛 `InvalidOperationException` |

实现：内部 `_inputIssued`（本节点是否已输出过战斗输入）。`CreateBattleInput` 置 true；`ApplyResult` 成功后置 false（失败则 `IsFailed` 已挡住后续）。同一节点多次 `CreateBattleInput` 都只是置 true，不推进。

不要做成"第二次胜利当 no-op"。

## 5. 测试策略

`RunStateTests`（测试内自己拼牌组 / 敌人 / 遗物 Id，不读 SO）：

- 开局满血、`NodeIndex == 0`、`Gold == 0`、`IsOver == false`。
- `CreateBattleInput`：`Setup.PlayerCurrentHp` 等于 Run 当前生命；牌组是拷贝且**顺序与 Run 牌组相同**（改返回列表不影响 Run；两次输入彼此顺序也相同，证明 Run 没洗）；遗物是新实例（两次 `CreateBattleInput` 的遗物不是同一引用）；敌人是 `encounters[nodeIndex]`。
- 残血写回：`ApplyResult(true, 50)` 后下一场 `Setup.PlayerCurrentHp == 50`。
- `AddCard` 后下一场牌组含新卡；原 10 张仍在。
- 三场胜利后 `IsCleared`：`AddCard` 成功，牌组张数 +1；再 `CreateBattleInput` / `ApplyResult` 仍抛。失败后 `AddCard` 抛。
- 消耗 / 弃牌不写回：测试辅助 `new BattleSession(input.Setup, …)`，打出消耗牌，`ApplyResult(true, hp)` 后 Run 牌组张数与内容不变。
- 同一 `runSeed` + 同一 `nodeIndex`：两次 `CreateBattleInput` 的 `Random` 种子相同（用双方 `Next()` 若干次相等，或自算 `unchecked(seed * 397 ^ node)` 再 `new Random` 对照）。`nodeIndex` 不变。对照 `Next()` 只发生在测试里，不要在 `CreateBattleInput` 里预支。
- 不同节点：`f(seed, 0) != f(seed, 1)`（对常用种子成立即可；公式本身不同）。
- `ApplyResult` 拒绝：同一节点两次胜利抛且 `NodeIndex` 仍为 1；失败后再 `ApplyResult` / `CreateBattleInput` 抛；三场胜利后再 `ApplyResult` / `CreateBattleInput` 抛；`won: true, remainingHp: 0` 抛且 `IsFailed == false`、`NodeIndex` 不变；`won: true, remainingHp: MaxHp + 1` 抛且状态不变。
- 构造：`encounters` 不是 3 条、重复遗物 Id、未知遗物 Id、null 牌组、`relicIds == null` 抛；`relicIds: []` 通过。

`CombatantStateTests`：`new CombatantState(80, 50)` 当前 50；`current > max` / `<= 0` 抛；单参仍满血。`BattleSetup` 三参 `PlayerCurrentHp == MaxHp`；四参残血；四参 `0` / `> max` / 负值抛（不新增根目录测试文件，写在 `CombatantStateTests` 或 `BattleSessionTests` 里）。

`BattleSessionTests`：`new BattleSetup(40, 3, 5, 20)` 开战 `Player.CurrentHp == 20`。既有 `CreateSession` 仍三参 Setup，0.x 断言不改。

**grep 范围（本刀验收，不要写成全 Runtime）：** 在 `Assets/Scripts/Runtime/Core/Run/` 以及本刀**新增**的 Runtime 文件里搜不到 `new BattleSession`。`BattleController.Awake` 那一处是 0.x `TestScene` 单场，不算本刀范围。测试辅助与 `BattleSessionTests.CreateSession` 可以 `new`。

## 7. 关键技术决策

| 决策 | 1.0 选择 | 原因 |
| --- | --- | --- |
| 进战斗返回值 | [已定] `BattleInput` 五个字段 | 返回 Session 会让 Run 依赖战斗生命周期；返回"元组/匿名包"测试与 1.1 都不好接 |
| 牌组拷贝 | [已定] 浅拷贝引用列表 | `CardDefinition` 不可变；深拷贝没有消费者 |
| 遗物实例 | [已定] 每场 `RelicFactory.Create` | 开战钩子每场再打一次；不把上一场 `CombatantState` 上的对象拿回来 |
| `Random` 所有权 | [已定] 交给调用方；Run 不持有 | 用完即弃；同一节点多次 `CreateBattleInput` 各拿一个同种子实例 |
| 战斗种子 | [已定] `unchecked(runSeed * 397 ^ nodeIndex)` | 稳定、可自算；不用 `HashCode.Combine` |
| 当前生命怎么进 Session | [已定] `BattleSetup` 四参；三参重载 = 满血 | 不改 Session 构造其余签名；0.x 三参调用一行不改。不用 `< 0` 哨兵 |
| `ApplyResult` 重复 | [已定] 抛异常，状态不变 | 静默 no-op 会让 `nodeIndex` 偷偷 +2 |
| 失败是否写生命 | [已定] 不写、不推进 | 失败 Run 作废；结束页摘要不依赖残血写回 |
| 本版谁 `new Session` | [已定] 测试辅助；`Core.Run` 与新增文件禁止 | `BattleController` 那一处留给 1.1 改 `Begin` |
| 内容真相 | [已定] 测试直接 `new RunState(...)` | 本版无 `RunConfig`，避免与 `BattleConfig` 两套真相 |
| `AddCard` 通关后 | [已定] 允许；只在 `IsFailed` 或 null 拒绝 | `IsCleared` 表示没有下一场战斗，不表示牌组冻结。第三场胜利先写回再奖励，不能把加卡锁在写回之前 |

## 8. 完成定义

- `BattleSetup` 三参调用与 `BattleConfig.ToSetup()` 不改；0.x 测试不改断言通过。
