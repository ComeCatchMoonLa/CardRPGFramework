# 开发计划

> **本文件夹是什么**：项目按版本推进的唯一入口。Phase 1 / 2 交出的局内战斗框架定为 **0.1**；之后按「先大版本大纲、再小版本细化」写文档，只为最近的一两个小版本写全套细化。
>
> **本文件夹不是什么**：不是《杀戮尖塔》内容清单。原版有数百张卡、百余遗物、约 123 种能力，这里只挑能多证明一个架构边界的内容做标本。规则事实以 [`../详细游戏设计文档参考/README.md`](../详细游戏设计文档参考/README.md) 与 [`../杀戮尖塔机制研究.md`](../杀戮尖塔机制研究.md) 为准，挂钩位置以 [`../Phase 2 扩展边界批注.md`](../Phase%202%20扩展边界批注.md) 为准。

## 1. 版本号约定

两段式 `主.次`，只用这两段，不做补丁号。

| 版本段 | 含义 | 判据 |
| --- | --- | --- |
| **0.x** | 局内战斗还在补「卡牌战斗该有的东西」 | 没有局外闭环，一场打完就结束，不算完整游戏 |
| **1.0** | 第一次能从开局打到结束的完整（短）Run | 局内 + 局外接通；`BattleSession` 之外有 `RunState` |
| **1.x** | 在闭环上做交付打磨与扩展 | 出包、演示、导表、多敌人、更多挂钩标本 |

- **0.1 = Phase 1 + Phase 2a/2b/2c**，已完成。文档在 [`Ver 0.x/0.1/`](Ver%200.x/0.1/)，其中 [`MVP计划与迭代计划.MD`](Ver%200.x/0.1/MVP计划与迭代计划.MD) 是当时的总计划，现在只当历史。
- **一个小版本 = 一条能独立验收、能多讲清一个边界的功能**，按功能切、不按工期切：体量可以从一两天到四五天不等。有硬耦合的东西（没有 A 则 B 是空接口或测不出正确语义）捆在同一版，其余各自成版。沿用 `游戏设计.md` / `技术设计.md` / `TODO.md` 三件套。
- 小版本完成的标志：TODO 全部勾完、验收标准满足、EditMode 全绿、提交并推送。

## 2. 细化深度规则

只给**下一个**和**下下个**小版本写全三件套；更远的只写游戏设计或大纲，进入前再补技术设计与 TODO。

原因：`MVP计划与迭代计划.MD` 后半（Luban、回放、热更）写得太远，Phase 2 做完就已经和实际判断不一致。技术设计一旦写下接口形状，隔两个版本再看多半要重写；游戏设计（做什么、为什么、验收）过期得慢得多。

例外：因为重切版本而**提前存在**的技术设计 / TODO 不删，文首标「草稿」，进入该版本前对照前面版本的实际实现复核后再转正；它们不算"已细化"，接口形状以复核后的为准。（0.4 / 0.5 的都按这条走完了：各自在前一版完成后转正并已完成。0.6 已完成；0.7 是下一个版本，它的技术设计与 TODO 随 0.6 一并写成草稿，已在 0.7 TODO 第 0 节对照 0.6 实际实现复核转正——复核是 0.7 自己的第一步，不算在 0.6 里。1.0 目前只有游戏设计。）

## 4. 三条总原则

1. **下一刀必须多讲清一个边界。** 多一张「打击但 8 点」不算进度；痛击（复合效果）、消耗堆（类型决定去向）、纸鹤（遗物改公式常数）才算。
2. **有消费者才加原语。** 抽牌效果、消耗堆、遗物列表、`OnTurnEnd`，都要在同一个版本里配上使用它的卡或遗物，不留空接口。
3. **123 种能力不等于 123 套系统。** 差的是挂钩点（回合开始/结束、施加前后、公式常数、格挡前 Final……），不是再做一个 Buff 引擎。新能力多数是新的 `BuffState` 子类，或给已有触发接口多一个方法。
