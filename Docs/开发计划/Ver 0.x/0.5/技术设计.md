# 0.5 技术设计：遗物三钩子

> 本文由原"0.3 消耗堆、能力牌、遗物"的技术设计按功能拆出，在 0.4 完成后对照 0.2～0.4 的实际实现（`ToAction` 每次用 `BuffFactory.Create` 新建 `BuffState` 再交给 `ApplyBuffAction`、`TriggerTurnStartBuffs` 的 `foreach` + `is` + `RunAll`、`BattleSession` 构造函数形状、`DamageContext` 只有 `Source` / `Target`、Data 层 SO 校验不写单测）复核过接口形状，四处 [待确认] 已定（第 7 节），已转正。
>
> **技术目标：新增 `Core.Relics`，遗物挂在 `CombatantState` 的独立列表上，钩子接口沿用 `IBuffTrigger` 的形状——固定时机遍历列表、调虚方法，不做事件总线。三件遗物分别接在开战、施加 Buff 之前、`WeakDamageRule` 内部三个位置。**
>
> 这是 Phase 2b 给 `ApplyBuffAction` 补 `source` 参数之后第一次有人消费它（蛇颅骨）。

## 1. 技术原则

延续 0.1～0.4 的优先级：**正确性 > 可测试性 > 可读性 > 当前已知需求的扩展性**。补充：

- 遗物钩子和 Buff 触发是**同一种形状**：一个接口一个方法，实现者自己决定做什么；调用方只在固定时机 `foreach` + 类型判断。不引入订阅 / 广播。
- 钩子只在有消费者时才存在：本版本只有 `IBattleStartRelic` 与 `IApplyBuffModifier` 两个接口，纸鹤不需要接口（它是被规则读的数据，和虚弱 Buff 被规则读一样）。
- **钩子里只入队 Action，不直接改状态**：金刚杵在 `OnBattleStart` 里 `queue.Enqueue(new ApplyBuffAction(...))`，不写 `owner.ApplyBuff(...)`——与 `IBuffTrigger` 的约定相同（批注第 2 节"触发遍历中只入队 Action"）。这样开战给的力量和打出力量强化走的是同一条路径，蛇颅骨那类施加钩子对它一视同仁。
- **Buff 实例只由 `BuffFactory` 按 Id 创建**：金刚杵写 `BuffFactory.Create(BuffIds.Strength, 1)`，不写 `new StrengthBuff(1)`；遗物是"内容"，和卡牌一样只认 Id，不认 Buff 的具体类型。
- **`BattleSession` 只认接口，不认遗物**：Session 里允许出现的遗物相关符号只有 `RelicState`（构造参数类型）与 `IBattleStartRelic`（开战遍历）；不出现 `RelicIds`、任何具体遗物类、也不按遗物 Id 分支。同理 `ApplyBuffAction` 只认 `IApplyBuffModifier`。改公式常数的遗物（纸鹤）改的是对应 Rule 一处，Session 仍然不知道它存在。
- Buff Id 字面量收进 `Core.Buffs.BuffIds`，作为本版本第一步单独提交（第 4.1 节末尾、第 7 节）；遗物是第三个消费这批字符串的层，再复制一遍字面量就是第三份真相。

## 2. 分层与依赖

```text
Views（BattleView：遗物栏行）
  ↓ 只读
Controllers（BattleController：把配置的遗物交给 Session；RelicDisplayName(id)）
  ↓
Core.Battle（BattleSession：构造时接收遗物；StartBattle 触发开战钩子）
  ↓
Core.Relics（新：RelicState / RelicIds / IBattleStartRelic / IApplyBuffModifier / VajraRelic / SneckoSkullRelic / PaperKraneRelic / RelicFactory）
Core.Combatants（CombatantState：Relics 列表、AddRelic、HasRelic）
Core.Actions（ApplyBuffAction：执行前遍历 source.Relics 的 IApplyBuffModifier）
Core.Rules（WeakDamageRule：倍率由 target.HasRelic 决定）
Core.Buffs（BuffIds：新的常量类；BuffFactory / 四个 Buff / 三条 Rule / BuffDisplayNames 改为引用它）
```

依赖说明：

- `Core.Relics` 引用 `Core.Actions` / `Core.Buffs` / `Core.Combatants`（金刚杵要入队 `ApplyBuffAction`），`Core.Actions` 又引用 `Core.Relics`（`IApplyBuffModifier`），`Core.Combatants` 引用 `Core.Relics`（`RelicState`）。命名空间互引在 0.1 就存在（`Core.Buffs.IBuffTrigger` 与 `Core.Actions` 互引），单一程序集内不构成问题；边界靠"谁负责什么"而不是靠编译隔离。1.1 拆 asmdef 时 `Core` 整体是一个程序集，不会拆到命名空间粒度。
- `Core.Rules` 读 `CombatantState.HasRelic`，仍然只读状态、只写 `Damage`，规则仍是纯函数。`DamageContext` 不改。
- `Core.Relics` 不引用 `UnityEngine`。

## 4. 核心接口

### 4.1 遗物与 BuffIds

```csharp
namespace CardRPGFramework.Core.Buffs
{
    /// 四个 Id 字面量的唯一出处。Data 资产里的 buffId、Views 的显示名表、Rule 的 HasBuff 都对着这里。
    public static class BuffIds
    {
        public const string Strength = "strength";
        public const string Poison = "poison";
        public const string Weak = "weak";
        public const string Vulnerable = "vulnerable";
    }
}

namespace CardRPGFramework.Core.Relics
{
    /// 只有 Id。没有层数、没有衰减；将来带计数的遗物在子类里自己加字段，基类不预留。
    public abstract class RelicState
    {
        public abstract string Id { get; }
    }

    public static class RelicIds
    {
        public const string Vajra = "vajra";
        public const string SneckoSkull = "snecko_skull";
        public const string PaperKrane = "paper_krane";
    }

    /// 与 IBuffTrigger.OnTurnStart 同形：只入队 Action，不直接改状态。
    /// 签名里没有对手：本版本三件都不需要（弹珠袋"开战给敌人易伤"出现时再加参数）。
    public interface IBattleStartRelic
    {
        void OnBattleStart(CombatantState owner, ActionQueue queue);
    }

    /// 施加 Buff 执行之前的一次机会：只允许修改即将施加的这个 buff 实例（层数），
    /// 不提供取消、不提供追加——两者当前都没有消费者（人工制品 / 冠军腰带）。
    public interface IApplyBuffModifier
    {
        void ModifyOutgoingBuff(CombatantState source, CombatantState target, BuffState buff);
    }

    public sealed class VajraRelic : RelicState, IBattleStartRelic
    {
        public override string Id => RelicIds.Vajra;

        // 走工厂、走 Action：与打出力量强化同一条路径，不 new StrengthBuff、不 owner.ApplyBuff。
        public void OnBattleStart(CombatantState owner, ActionQueue queue) =>
            queue.Enqueue(new ApplyBuffAction(owner, owner, BuffFactory.Create(BuffIds.Strength, 1)));
    }

    public sealed class SneckoSkullRelic : RelicState, IApplyBuffModifier
    {
        public override string Id => RelicIds.SneckoSkull;

        // 按 Id 判定而不是"所有施加 +1"：金刚杵开战给的力量也会经过这里，但什么都不发生。
        public void ModifyOutgoingBuff(CombatantState source, CombatantState target, BuffState buff)
        {
            if (buff.Id == BuffIds.Poison)
            {
                buff.AddStacks(1);
            }
        }
    }

    /// 没有钩子：它是被 WeakDamageRule 读取的数据，和虚弱 Buff 被规则读取是同一种关系。
    public sealed class PaperKraneRelic : RelicState
    {
        public override string Id => RelicIds.PaperKrane;
    }

    /// 与 BuffFactory 同理：switch 穷举，IsKnown 与 Create 两处 Id 列表必须同步改。
    public static class RelicFactory
    {
        public static bool IsKnown(string id) => id is RelicIds.Vajra or RelicIds.SneckoSkull or RelicIds.PaperKrane;

        public static RelicState Create(string id) => id switch
        {
            RelicIds.Vajra => new VajraRelic(),
            RelicIds.SneckoSkull => new SneckoSkullRelic(),
            RelicIds.PaperKrane => new PaperKraneRelic(),
            _ => throw new ArgumentException($"未知的遗物 Id: {id}", nameof(id)),
        };
    }
}
```

**[已定] 施加钩子直接改传入的 `BuffState` 实例**，不引入 `ApplyBuffContext`。依据实现：`ToAction` 每次 `BuffFactory.Create` 新建一个 `BuffState` 交给 `ApplyBuffAction`，执行前这个实例还不在任何人的字典里，`AddStacks` 改的是"即将施加的量"，安全；`CombatantState.ApplyBuff` 之后无论是存入实例还是把层数加到已有 Buff 上，改过的层数都会落地。出现取消（人工制品）时再引入 Context 并加 `Cancelled`，那时也顺带需要 Buff / Debuff 极性标记，是另一个版本的事。

**[已定] 加 `BuffIds`，作为本版本第一步单独提交。** 替换范围只有 Runtime 的 9 个文件：四个 Buff 子类的 `Id`、`BuffFactory` 的 `IsKnown` / `Create`、三条 Rule 的 `HasBuff` / `GetBuffStacks`、`BuffDisplayNames` 的 case 标签（C# 9 的 `is ... or ...` 模式与 `switch` 表达式都接受 `const string`）。**测试文件里的字面量不改**：它们断言的是对外字符串契约，保留字面量正好锁住"常量值没被改动"（`BuffFactoryTests.IsKnown("strength")` 这类用例在常量改错时会红）。**`Assets/Data/Cards/*.asset` 里的 `buffId: strength` 也不改**：那是资产数据，正是这批常量要对上的字符串；"字面量只剩 `BuffIds.cs`"的 grep 核对范围限定在 `Assets/Scripts/Runtime`。这一步纯替换，跑完 165 项全绿单独 commit，再开始遗物；遗物切片的 diff 里就不夹带无关文件。

### 4.2 CombatantState

```csharp
public sealed class CombatantState
{
    private readonly List<RelicState> _relics = new();
    public IReadOnlyList<RelicState> Relics => _relics;

    /// 同 Id 重复添加抛 ArgumentException：遗物唯一，重复属于配置错误，不做静默合并。
    public void AddRelic(RelicState relic);
    public bool HasRelic(string id);
}
```

**[已定] 遗物挂在 `CombatantState` 上**，不做独立的 `RelicBag`。与一代一致（遗物在 `AbstractPlayer` 上，`AbstractPlayer` 是生物）；规则用 `context.Target.HasRelic` 就能读，`DamageContext` 与它的三个构造点（`DamageAction.Execute`、两个预览）以及 `DamageRuleTests` 里的构造都不用改；敌人的列表恒为空，没有额外成本。1.0 从 `RunState` 进战斗时也是把遗物 Id 列表经 `RelicFactory` 建成实例再 `AddRelic`，形状不变。

### 4.3 ApplyBuffAction

```csharp
public void Execute(ActionContext context)
{
    // 遍历的是施加方的遗物：蛇颅骨是"你施加中毒时"，不是"有人被施加中毒时"。
    foreach (var relic in _source.Relics)
    {
        if (relic is IApplyBuffModifier modifier)
        {
            modifier.ModifyOutgoingBuff(_source, _target, _buff);
        }
    }

    BuffEffect.Apply(_target, _buff);
}
```

敌人没有遗物，所以敌人施加的中毒（0.6 起可能出现）自然不受影响，不需要额外判断；0.7 敌人给玩家上虚弱也同理。构造函数上那段"source 本阶段没有任何消费者"的注释改成指向本节。

### 4.4 WeakDamageRule

```csharp
public sealed class WeakDamageRule : IDamageRule
{
    private const double DefaultMultiplier = 0.75;
    private const double PaperKraneMultiplier = 0.6;

    public void Apply(DamageContext context)
    {
        if (!context.Source.HasBuff(BuffIds.Weak)) return;
        var multiplier = context.Target.HasRelic(RelicIds.PaperKrane) ? PaperKraneMultiplier : DefaultMultiplier;
        context.Damage *= multiplier;
    }
}
```

读的是**目标**的遗物：纸鹤是"打你的虚弱敌人更弱"，持有者是被打的一方。玩家自己带虚弱去打敌人时，目标（敌人）没有纸鹤，仍用 0.75——这正是原版语义，也是测试要覆盖的反例。仍然按"有无"乘倍率，不按层数。0.3 的预览走同一个 `DamageCalculator`，`PreviewEnemyAttack()` 自动从 4 变 3。这是 Rule 里第一次出现遗物 Id，也是本版本 Session 之外唯一一处"知道某件具体遗物"的 Core 代码；纸蛙（易伤 1.5 → 1.75）出现时是 `VulnerableDamageRule` 里同样的一行，不是新机制。

### 4.5 BattleSession

```csharp
public BattleSession(BattleSetup setup, IEnumerable<CardDefinition> deck, Random random,
                     IEnumerable<RelicState> relics = null)
{
    // ...0.1 的初始化
    foreach (var relic in relics ?? Array.Empty<RelicState>()) Player.AddRelic(relic);
}

public void StartBattle()
{
    if (Phase != BattlePhase.NotStarted) return;
    TriggerBattleStartRelics(Player);   // 遍历 Player.Relics 的 IBattleStartRelic，随后 RunAll
    StartPlayerTurn();
}
```

- `relics` 用可选参数：0.1～0.4 的测试构造 Session 的地方不用改；`CreateSession` 辅助方法加一个同名可选参数。
- `TriggerBattleStartRelics` 的形状与 `TriggerTurnStartBuffs` 一致（`foreach` + `is` + `RunAll`），放在 `StartPlayerTurn()` 之前：金刚杵的力量在第一回合开始前就到位，Buff 行从第一回合就显示 `力量 1`，回合开始的 Buff 触发（中毒）也能看到它。
- Session 不新增任何按遗物的公开成员：界面读遗物 Id 走 `Player.Relics`，与 Buff 行读 `Player.Buffs` 是同一条路径。

### 4.6 Data 层

```csharp
[CreateAssetMenu(fileName = "RelicData", menuName = "CardRPG/Relic Data")]
public sealed class RelicData : ScriptableObject
{
    [SerializeField] private string id;
    [SerializeField] private string displayName;
    public string Id => id;
    public string DisplayName => displayName;
    public RelicState ToState() => RelicFactory.Create(id);
    public bool TryValidate(out string error);   // id 非空且 RelicFactory.IsKnown；displayName 非空
}

public sealed class BattleConfig : ScriptableObject
{
    // ...既有字段
    [SerializeField] private List<RelicData> relics = new();   // 允许为空：没有遗物也是合法配置
    public IReadOnlyList<RelicData> Relics => relics;
    public List<RelicState> ToRelicStates();
    // TryValidate 增加：relics 无空引用、各自 TryValidate 通过、Id 不重复（同一资产引用两次也算重复）
}
```

`displayName` 放在 `RelicData` 里而不是代码里：和 `CardData` 一致，内容在 Inspector 里命名。与 `CardData` / `BattleConfig` 相同，SO 的 `TryValidate` 不写 EditMode 单测（现有 Data 单测只有可 `new` 的 `EffectSpecData`）：Id 合法性的逻辑在 `RelicFactory.IsKnown`（有测试），重复与空引用的检查靠联调时故意配错一次看 Console（第 5 节）。

### 4.7 表现层

**[已定] 显示名走 Controller，不新增 `Views/RelicDisplayNames`。**

- `BattleController`：`Awake` 里 `new BattleSession(setup, deck, random, battleConfig.ToRelicStates())`；新增 `string RelicDisplayName(string id)`，从 `battleConfig.Relics` 建一份 Id → displayName 字典，未知 Id 原样返回（与 `BuffDisplayNames` 同一条兜底规则，启动校验已经拦过未知 Id）。不另加 `RelicIds` 列表：View 经 `battleController.Player.Relics` 读 Id，与 Buff 行同路径。
- `BattleView`：新增 `[SerializeField] TMP_Text relicsText`，`Refresh` 里写 `遗物：金刚杵  蛇颅骨  纸鹤`（两个空格连接，与 Buff 行一致）；没有遗物时写 `遗物：无`。文字即可，不做图标。
- 场景：`TopBar` 下补一个文本对象（可 Duplicate `PileCounts`）并接线。

## 5. 测试策略

按 0.3 的做法**锁预览再比结算**，不要只和 Rule 对拍；蛇颅骨走**打出剧毒**，不要用 `CombatantState.ApplyBuff` 直调。

- `BattleSessionTests.Relics.cs`（新 partial；`CreateSession` 加 `relics` 可选参数）：
  - 金刚杵：`StartBattle` 后 `Player.GetBuffStacks(BuffIds.Strength) == 1`，`Player.Buffs` 里只有力量这一条；`PreviewPlayerAttack(6) == 7`，打出攻击后敌人 HP 差值为 7；无遗物时力量 0、预览 6。
  - 蛇颅骨：打出剧毒后 `Enemy.GetBuffStacks(BuffIds.Poison) == 4`；无遗物时 3；**只配蛇颅骨**时打出力量强化仍是 2 层（按 Id 判定；若带金刚杵会是 3，那 1 层来自开战注入，用例里不要混）。
  - 纸鹤：先打虚弱给敌人，`PreviewEnemyAttack() == 3`，结束回合后玩家 HP 差值为 3（0 格挡）；无纸鹤时预览 4、掉 4；玩家自己带虚弱（`Player.ApplyBuff(new WeakBuff(1))` 构造）且持有纸鹤时 `PreviewPlayerAttack(6) == 4`（0.75，不是 0.6）。
  - 三件同时配置：`Player.Relics.Count == 3`，`Player.Buffs` 里只有力量；`Player.Buffs` 中没有任何 Id 等于 `RelicIds.*`。
- `CombatantStateTests`：`AddRelic` 后 `HasRelic` 为 true、`Relics.Count` 为 1；重复 Id 抛 `ArgumentException`；`HasRelic` 对未持有的 Id 为 false。用测试内定义的 `RelicState` 子类（与 `ActionQueueTests.RecordingAction` 同一做法）：容器测试不该依赖三件具体遗物，而且 TODO 第 1 节写它时三个类还不存在。
- `RelicFactoryTests`（新，随第 2 节三个遗物类一起）：三个 Id 各返回正确类型；`IsKnown` 三真一假；未知 Id 抛 `ArgumentException`。
- `ActionQueueTests`：施加方持有蛇颅骨、Buff 是中毒 → 目标 4 层；Buff 是力量 → 2 层不变；施加方没有遗物 → 不变；**目标**持有蛇颅骨、施加方没有 → 不变（钩子看施加方）。
- `DamageRuleTests`：`WeakDamageRule` 在目标持有纸鹤时 6 → 3.6、否则 4.5；纸鹤在**施加方**身上不生效；2 层与 1 层结果相同。
- `BuffIds` 那一步不新增测试：0.1～0.4 的 165 项不改断言全绿即是验收。
- Data：不写 SO 单测（4.6）。

预计新增约 20 项，总数约 185。0.1～0.4 全部测试不改断言通过。

## 6. 排除项

- 不做 `IApplyBuffModifier` 的取消 / 追加能力，不做 Buff 极性标记。
- 不做遗物的回合开始 / 结束钩子、计数字段。
- 不改 `LoseHp`、`TakeDamage`（钨条 / 鸟居 / 无实体三处挂钩点都不动）。
- `IBattleStartRelic` 不带对手参数（弹珠袋"开战给敌人易伤"出现时再加）。
- 不做纸蛙 / 怪异蘑菇：与纸鹤同一种钩子，多做一件不多证明任何边界。
- 不做遗物获取流程与 UI 图标；不做 `Views/RelicDisplayNames`。

## 7. 关键技术决策

| 决策 | 0.5 选择 | 原因 |
| --- | --- | --- |
| 施加钩子形状 | [已定] 直接改传入的 `BuffState`，不引入 `ApplyBuffContext` | 实例在执行前不在任何字典里，`AddStacks` 已存在；取消 / 追加没有消费者 |
| Buff Id 字面量 | [已定] 加 `BuffIds`，作为第一步单独提交；测试保留字面量 | 遗物是第三个消费这批字符串的层；单独提交让遗物切片不夹带 9 个无关文件 |
| 遗物存放位置 | [已定] `CombatantState.Relics` | 与一代一致；规则直接读目标 / 施加方，不改 `DamageContext` |
| 遗物显示名 | [已定] `RelicData.displayName` + `BattleController.RelicDisplayName(id)` | 内容在 Inspector 里命名，与 `CardData` 一致；View 不依赖 Data 类型；不留 `RelicDisplayNames` 第二套 |
| 钩子形状 | 一接口一方法，固定时机 `foreach` | 与 `IBuffTrigger` 同形；批注第 5 节明确不做 EventBus |
| 钩子里怎么做事 | 只入队 Action；Buff 实例只经 `BuffFactory` | 与 `IBuffTrigger` 约定相同；开战给的力量与打牌给的力量同一条路径 |
| 施加钩子能力 | 只能改即将施加的层数 | 取消 / 追加没有消费者 |
| 纸鹤怎么实现 | `WeakDamageRule` 读目标是否持有 | 改公式常数属于 Rule；不加层数、不再乘一层（批注第 3 节） |
| 遗物实例化 | `RelicFactory` 的 `switch` | 与 `BuffFactory` 同理 |
| Session 知道多少 | 只认 `RelicState` / `IBattleStartRelic` | 新遗物 = 类 + 工厂一行 + 资产；改常数的遗物改 Rule 一处 |

## 9. 扩展边界批注（非本阶段范围）

> - **人工制品 / 冠军腰带**：需要施加钩子能取消、能在成功后追加另一次施加，以及 Buff / Debuff 极性；届时把 `IApplyBuffModifier` 升级为带 `ApplyBuffContext` 的前后两个钩子，并把人工制品做成 **Buff**（它在原版是 Power，不是遗物）。
> - **弹珠袋**（开战给所有敌人 1 易伤）：`IBattleStartRelic.OnBattleStart` 要能拿到对手，届时加参数或改传 Session 侧的上下文；本版本三件都只碰持有者自己。
> - **纸蛙 / 怪异蘑菇**：`VulnerableDamageRule` 里与 4.4 相同的一行，分别读目标 / 施加方是否持有。
> - **钨条 / 鸟居 / 无实体**：三个互不相同的挂钩点（`LoseHp` 前 / 格挡后仅 Attack / 格挡前 Final），位置见 [`../../../Phase 2 扩展边界批注.md`](../../../Phase%202%20扩展边界批注.md) 第 2 节；每种一件标本即可，不要因为有了遗物栏就一次做完。
> - **遗物的回合钩子**（例如回合开始获得格挡）：加 `ITurnStartRelic` 与 `TriggerTurnStartBuffs` 同位置遍历即可；有消费者再加。
> - **带计数的遗物**：计数字段放在子类里，`RelicState` 基类不预留。
> - **1.0 从 Run 带遗物进战斗**：`RunState` 存遗物 Id 列表，进战斗时 `RelicFactory.Create` 建实例走同一个构造参数；`BattleConfig.relics` 是否保留给 `TestScene` 单场调试与 1.0 的 `RunConfig` 取舍一并决定。
